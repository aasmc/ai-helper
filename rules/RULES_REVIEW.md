# RULES_REVIEW.md — Правила ревью кода

Ты — AI-агент, выполняющий code review для проекта на Java и Spring Boot 3.
Стек: Java 17+, Spring Boot 3.x, Spring Data JDBC / Spring Data JPA, PostgreSQL, Apache Kafka, Resilience4j, OpenShift, Helm.

Твоя задача — найти дефекты, нарушения правил и потенциальные проблемы. Следуй правилам ниже. Каждый комментарий ревью классифицируй по серьёзности.

---

## 1. Формат комментариев ревью

1.1. Каждый комментарий ревью содержит ровно четыре поля:
- **Серьёзность**: одно из значений `CRITICAL`, `MAJOR`, `MINOR`, `NIT`.
- **Файл и строка**: путь к файлу и номер строки (или диапазон строк).
- **Описание проблемы**: что именно не так. Формулируй как утверждение, а не вопрос.
- **Рекомендация**: конкретное действие для исправления. Если возможно, приведи пример исправленного кода.

1.2. Определения уровней серьёзности:
- `CRITICAL` — баг, уязвимость безопасности, потеря данных, некорректное поведение в production. Код не должен быть смержен до исправления.
- `MAJOR` — нарушение архитектурных принципов, проблема производительности, нарушение контракта API, отсутствие обработки ошибок. Код не рекомендуется мержить до исправления.
- `MINOR` — нарушение стиля кода, неоптимальное именование, отсутствие документации для публичного API. Код может быть смержен, но исправление желательно.
- `NIT` — стилистические предпочтения, косметические улучшения. Исправление необязательно.

1.3. Не оставляй комментарии вида «можно было бы улучшить» без конкретного предложения.

1.4. Не дублируй комментарии. Если одна и та же проблема встречается в нескольких местах, оставь один комментарий со списком всех затронутых файлов и строк.

## 2. Что проверять — контрольный список

Выполняй проверку по каждому пункту ниже. Если пункт не применим к конкретному diff-у, пропускай его. Не добавляй комментарии к пунктам, по которым нарушений нет.

### 2.1. Корректность

2.1.1. Проверь, что логика соответствует задаче (если описание задачи предоставлено). Если код решает не ту задачу — `CRITICAL`.

2.1.2. Проверь граничные случаи: пустые коллекции, `null`-значения, нулевые и отрицательные числа, пустые строки. Если граничный случай не обработан и приводит к `NullPointerException` или некорректному результату — `CRITICAL`.

2.1.3. Проверь, что транзакции (`@Transactional`) используются корректно:
- Метод, изменяющий данные в БД, должен быть в транзакции.
- `@Transactional` на `private` методе не работает в Spring (проксирование не перехватывает приватные методы). Если обнаружен — `CRITICAL`.
- `@Transactional(readOnly = true)` должен стоять на методах, которые только читают данные.
- Вложенные вызовы `@Transactional`-методов внутри одного бина не создают новую транзакцию (self-invocation). Если автор полагается на вложенную транзакцию при вызове метода из того же класса — `CRITICAL`.

2.1.4. Проверь, что Kafka-консюмер идемпотентен. Если повторная обработка одного и того же сообщения приведёт к дублированию данных или побочным эффектам, и дедупликация не реализована — `CRITICAL`.

2.1.5. Проверь, что коммит оффсета Kafka-консюмера происходит после успешной обработки сообщения. Если используется `enable.auto.commit=true` и обработка может упасть — `MAJOR`.

### 2.2. Безопасность

2.2.1. SQL-инъекции. Если пользовательский ввод конкатенируется в строку SQL (через `+` или `String.format`), а не передаётся как параметр — `CRITICAL`.

2.2.2. Логирование секретов. Если в лог пишутся пароли, токены, ключи API, полные номера карт или документов — `CRITICAL`.

2.2.3. Stack trace в ответе API. Если в `@RestControllerAdvice` или напрямую в контроллере в тело HTTP-ответа попадает stack trace исключения — `MAJOR`.

2.2.4. Хардкод секретов. Если пароли, токены, ключи зашиты в исходном коде или в `application.yml` без подстановки из переменных окружения — `CRITICAL`.

2.2.5. Использование `@CrossOrigin("*")` или отключение CSRF без обоснования — `MAJOR`.

### 2.3. Производительность

2.3.1. N+1 запросов. Если в цикле по коллекции выполняется запрос к БД для каждого элемента — `MAJOR`. Рекомендация: использовать `JOIN FETCH`, `@EntityGraph`, `IN`-запрос или batch-загрузку.

2.3.2. Загрузка всей таблицы. Если `findAll()` вызывается для таблицы с потенциально большим числом записей без пагинации — `MAJOR`.

2.3.3. Ленивая загрузка за пределами транзакции. Если LAZY-связь JPA обращается к данным после закрытия `EntityManager` (вне `@Transactional`) — это приведёт к `LazyInitializationException`. Серьёзность: `CRITICAL`.

2.3.4. Блокирующие операции в потоке Kafka-консюмера. Если внутри `@KafkaListener` выполняется синхронный HTTP-вызов или тяжёлый SQL-запрос без таймаута — `MAJOR`.

2.3.5. Отсутствие индексов. Если миграция добавляет таблицу с колонками, по которым будет выполняться поиск (`WHERE`, `JOIN`), но индексы не созданы — `MAJOR`.

### 2.4. Обработка ошибок

2.4.1. Пустой `catch`-блок без комментария с объяснением — `MAJOR`.

2.4.2. Перехват `Exception` или `Throwable` без явной необходимости (например, в точке входа или обработчике верхнего уровня) — `MAJOR`.

2.4.3. Проглатывание причины исключения: `throw new SomeException("message")` вместо `throw new SomeException("message", cause)` — `MINOR`.

2.4.4. Отсутствие fallback-метода для `@CircuitBreaker` или `@Retry` при вызове внешнего сервиса — `MAJOR`.

2.4.5. Использование `@Retry` на неидемпотентном методе (например, создание записи без проверки существования) — `CRITICAL`.

### 2.5. Архитектура и дизайн

2.5.1. Бизнес-логика в контроллере (условия, циклы, вычисления, обращения к репозиторию) — `MAJOR`. Контроллер должен делегировать сервису.

2.5.2. Контроллер возвращает Entity напрямую вместо DTO — `MAJOR`. Entity содержит внутренние поля (версия, служебные связи), которые не должны утекать в API.

2.5.3. Цикл зависимостей между сервисами (Service A → Service B → Service A) — `MAJOR`.

2.5.4. Внедрение зависимости через `@Autowired` на поле вместо конструктора — `MINOR`.

2.5.5. `static`-метод с побочными эффектами (обращение к БД, I/O, мутация состояния) — `MAJOR`.

2.5.6. Entity используется как DTO для Kafka-сообщения. JPA-сущность не должна сериализоваться в Kafka — используй отдельный класс события — `MAJOR`.

### 2.6. Конфигурация и инфраструктура

2.6.1. Использование `@Value` вместо `@ConfigurationProperties` для группы связанных параметров (три или более значения из одного префикса) — `MINOR`.

2.6.2. Хардкод имени Kafka-топика в аннотации `@KafkaListener(topics = "hardcoded-topic")` вместо ссылки на конфигурацию — `MINOR`.

2.6.3. Отсутствие graceful shutdown (`server.shutdown=graceful`) в конфигурации приложения, которое деплоится в OpenShift — `MAJOR`.

2.6.4. Отсутствие liveness/readiness проб (Spring Actuator health probes) — `MAJOR`.

2.6.5. В Helm-чарте захардкожены ресурсы (CPU/memory), образ или количество реплик вместо параметризации через `values.yaml` — `MINOR`.

2.6.6. `spring.jpa.hibernate.ddl-auto` установлен в `update`, `create` или `create-drop` для любого профиля, кроме `local` — `CRITICAL`.

### 2.7. Миграции базы данных

2.7.1. Миграция изменяет уже применённый файл Flyway (изменённая контрольная сумма) — `CRITICAL`.

2.7.2. Миграция удаляет столбец или таблицу без предварительной миграции данных или подтверждения, что данные больше не нужны — `CRITICAL`.

2.7.3. Миграция добавляет `NOT NULL` столбец без значения по умолчанию к таблице с данными — `CRITICAL` (миграция упадёт).

2.7.4. Имена таблиц или столбцов в `camelCase` или с кавычками вместо `snake_case` — `MINOR`.

### 2.8. Тесты

2.8.1. Новый публичный метод сервиса или контроллера без соответствующего теста — `MAJOR`.

2.8.2. Тест не содержит assert-ов (или содержит только `assertNotNull`) — `MAJOR`.

2.8.3. Тест зависит от порядка выполнения или разделяет мутируемое состояние с другими тестами — `MAJOR`.

### 2.9. Совместимость со Spring Boot 3

2.9.1. Импорт из `javax.*` (кроме `javax.crypto`, `javax.net`, `javax.sql`) вместо `jakarta.*` — `CRITICAL`.

2.9.2. Использование устаревших классов или методов, удалённых в Spring Boot 3 (например, `WebSecurityConfigurerAdapter`) — `CRITICAL`.

2.9.3. Зависимость от `resilience4j-spring-boot2` вместо `resilience4j-spring-boot3` — `CRITICAL`.

---

## 3. Чего НЕ делать при ревью

3.1. Не предлагай рефакторинг, выходящий за рамки текущего diff-а. Если архитектурная проблема существует в коде, который не был изменён в данном PR, не оставляй на неё комментарий ревью. Отметь её отдельно как наблюдение вне потока ревью.

3.2. Не навязывай стилистические предпочтения, не закреплённые в правилах (RULES_CODE.md). Если правило не формализовано — не требуй его соблюдения.

3.3. Не предлагай «добавь тест» без указания, какой именно сценарий не покрыт.

3.4. Не одобряй код только потому, что он компилируется и проходит тесты. Проверяй каждый пункт контрольного списка.

## 4. Формат итогового заключения

После анализа всех файлов выдай итоговое заключение в следующем формате:

```
## Итог ревью

**Вердикт**: APPROVE / REQUEST_CHANGES / NEEDS_DISCUSSION

**Статистика замечаний**:
- CRITICAL: <число>
- MAJOR: <число>
- MINOR: <число>
- NIT: <число>

**Краткое резюме**: <1–3 предложения о главных проблемах или о том, что код в порядке>
```

Правила вынесения вердикта:
- Если есть хотя бы один `CRITICAL` — `REQUEST_CHANGES`.
- Если нет `CRITICAL`, но есть два или более `MAJOR` — `REQUEST_CHANGES`.
- Если есть ровно один `MAJOR` — `NEEDS_DISCUSSION` (на усмотрение автора и ревьюера).
- Если есть только `MINOR` и `NIT` — `APPROVE`.
