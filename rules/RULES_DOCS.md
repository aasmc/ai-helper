# RULES_DOCS.md — Правила написания документации

Ты — AI-агент, пишущий документацию для проекта на Java и Spring Boot 3.
Стек: Java 17+, Spring Boot 3.x, Spring Data JDBC / Spring Data JPA, PostgreSQL, Apache Kafka, Resilience4j, OpenShift, Helm.

Пиши документацию на русском языке, за исключением: имён классов, методов, полей, топиков, таблиц и прочих технических идентификаторов (на английском, в оригинальном написании).

---

## 1. Виды документации

1.1. Ты создаёшь четыре вида документации. Каждый вид имеет свою аудиторию и формат.

| Вид | Аудитория | Формат | Где хранится |
|-----|-----------|--------|-------------|
| Javadoc | Разработчики, использующие API класса | Javadoc-комментарии в коде | В `.java`-файлах |
| README сервиса | Разработчики, впервые открывающие проект | Markdown | `README.md` в корне проекта |
| ADR (Architecture Decision Record) | Разработчики и архитекторы | Markdown | `docs/adr/` |
| API-документация | Потребители REST API (frontend, другие сервисы) | OpenAPI 3.0 (YAML) | `src/main/resources/openapi/` или автогенерация |

## 2. Javadoc

2.1. Javadoc пиши на английском языке.

2.2. Javadoc обязателен для:
- Каждого публичного класса (кроме DTO / record, если их назначение очевидно из имени).
- Каждого публичного метода сервисного слоя.
- Каждого endpoint-а контроллера.
- Каждого метода в интерфейсе репозитория, если он содержит кастомный `@Query`.

2.3. Javadoc НЕ нужен для:
- Геттеров, сеттеров, конструкторов, сгенерированных Lombok или являющихся частью `record`.
- Приватных методов (используй обычные `//`-комментарии при необходимости).
- Очевидных переопределений стандартных методов (`toString`, `equals`, `hashCode`).

2.4. Структура Javadoc для метода:
```java
/**
 * Первое предложение — краткое описание, что делает метод. Заканчивается точкой.
 *
 * <p>Дополнительные детали, если нужны: алгоритм, ограничения, побочные эффекты.
 *
 * @param orderId unique identifier of the order, must not be null
 * @param status target status to transition to
 * @return updated order with new status
 * @throws OrderNotFoundException if no order with given ID exists
 * @throws InvalidStatusTransitionException if transition from current to target status is not allowed
 */
```

2.5. Правила Javadoc:
- Первое предложение начинается с глагола в третьем лице: «Returns...», «Creates...», «Validates...». Не начинай с «This method...».
- Каждый `@param` описывает ограничения параметра: допустим ли `null`, есть ли диапазон допустимых значений.
- Каждый `@throws` описывает условие, при котором исключение выбрасывается.
- Не дублируй сигнатуру метода: не пиши `@param orderId the order ID` — это не добавляет информации. Пиши `@param orderId unique identifier of the order, must not be null`.
- Не пиши Javadoc, который пересказывает имя метода: если метод `calculateTotalPrice()`, не пиши `Calculates total price.` без дополнительных деталей. Добавь информацию, которую нельзя извлечь из сигнатуры: «Calculates total price including tax and discounts. Returns zero if the order has no items.»

## 3. README сервиса

3.1. Каждый микросервис содержит `README.md` в корне проекта.

3.2. Обязательные секции README:

### 3.2.1. Назначение сервиса
Одно-два предложения: что делает сервис и какую бизнес-функцию обеспечивает. Не описывай технологии — только бизнес-смысл.

### 3.2.2. Архитектурный контекст
- С какими сервисами взаимодействует (синхронно — REST, асинхронно — Kafka).
- Какие Kafka-топики продюсирует и консюмирует.
- Какие внешние системы вызывает.
Если есть диаграмма — ссылка на неё.

### 3.2.3. Технологии и версии
Таблица ключевых технологий с версиями:
```
| Технология     | Версия  |
|---------------|---------|
| Java          | 17      |
| Spring Boot   | 3.2.x   |
| PostgreSQL    | 16      |
| Apache Kafka  | 3.6     |
```

### 3.2.4. Локальный запуск
Пошаговая инструкция для запуска на локальной машине разработчика:
1. Какие инструменты установить (JDK, Docker).
2. Как поднять инфраструктуру (Docker Compose для PostgreSQL, Kafka).
3. Какую команду выполнить для запуска.
4. Как проверить, что сервис работает (URL health-check).

### 3.2.5. Переменные окружения
Таблица всех переменных окружения, требуемых сервисом:
```
| Переменная             | Обязательна | Значение по умолчанию | Описание                          |
|-----------------------|-------------|----------------------|-----------------------------------|
| DB_URL                | Да          | —                    | JDBC URL PostgreSQL               |
| DB_USERNAME           | Да          | —                    | Имя пользователя БД              |
| KAFKA_BOOTSTRAP_SERVERS | Да       | —                    | Адрес Kafka-брокера               |
| APP_LOG_LEVEL         | Нет         | INFO                 | Уровень логирования               |
```

### 3.2.6. API
Ссылка на OpenAPI-спецификацию или URL Swagger UI для локального окружения.

### 3.2.7. Деплой
Краткое описание: в какой кластер OpenShift деплоится, через какой Helm-чарт, как запустить деплой.

## 4. ADR (Architecture Decision Record)

4.1. ADR создавай для каждого архитектурного решения, которое:
- Выбирает одну технологию из нескольких альтернатив.
- Определяет способ интеграции между сервисами.
- Устанавливает паттерн обработки данных (например, outbox pattern для Kafka + БД).
- Изменяет структуру БД нетривиальным образом.

4.2. Формат ADR — файл Markdown по шаблону:

```markdown
# ADR-{номер}: {Краткое название решения}

**Дата**: ГГГГ-ММ-ДД
**Статус**: Предложено | Принято | Отклонено | Заменено ADR-{номер}

## Контекст

Описание проблемы или ситуации, требующей решения.
Факты, ограничения, требования. Без оценок.

## Рассмотренные варианты

### Вариант 1: {Название}
Описание варианта.
**Плюсы**: ...
**Минусы**: ...

### Вариант 2: {Название}
Описание варианта.
**Плюсы**: ...
**Минусы**: ...

## Решение

Какой вариант выбран и почему.

## Последствия

Что изменится в результате этого решения. Какие новые ограничения появятся.
Какие действия требуется выполнить.
```

4.3. Нумерация ADR сквозная: `ADR-0001`, `ADR-0002`, и т.д. Файлы именуй `0001-краткое-описание.md`.

4.4. Не удаляй и не изменяй принятые ADR. Если решение пересмотрено — создай новый ADR со статусом «Заменено ADR-{номер}» и измени статус старого на «Заменено ADR-{новый номер}».

## 5. API-документация (OpenAPI)

5.1. Каждый REST API сервиса документируй в формате OpenAPI 3.0.

5.2. Если используется автогенерация (springdoc-openapi), размести аннотации в контроллерах:
- `@Operation(summary = "...", description = "...")` на каждом endpoint-е.
- `@ApiResponse(responseCode = "...", description = "...")` для каждого возвращаемого HTTP-статуса.
- `@Schema(description = "...")` на полях DTO, если имя поля недостаточно описательно.

5.3. Если спецификация пишется вручную (contract-first), храни файл в `src/main/resources/openapi/api.yaml`.

5.4. Обязательные элементы OpenAPI-спецификации:
- `info.title` — имя сервиса.
- `info.version` — версия API.
- `info.description` — краткое описание назначения API.
- Для каждого endpoint-а: `summary`, `description`, `parameters`, `requestBody` (если есть), `responses` со всеми возможными статусами.
- Для каждого статуса ответа: `description` и `content` с примером (`example`).

5.5. Коды ответов документируй полностью:
- `200` / `201` / `204` — успешный ответ.
- `400` — ошибка валидации входных данных.
- `404` — ресурс не найден.
- `409` — конфликт (бизнес-правило нарушено).
- `500` — внутренняя ошибка сервера (без деталей реализации в описании).

## 6. Документация Kafka-контрактов

6.1. Для каждого Kafka-топика, который сервис продюсирует или консюмирует, создай описание в `docs/kafka-contracts/` или в секции README.

6.2. Описание контракта включает:
- Имя топика.
- Направление: продюсирует / консюмирует.
- Формат ключа сообщения (тип, пример).
- Формат значения сообщения (JSON-schema или пример с описанием полей).
- Заголовки (headers), если используются (например, `message-id`, `correlation-id`).
- Гарантии: at-least-once / exactly-once.
- Идемпотентность: как консюмер обрабатывает дубликаты.

6.3. Пример описания:
```markdown
## Топик: order-events

**Направление**: Продюсер
**Ключ**: `orderId` (String, UUID)
**Формат значения**: JSON

### Схема значения
| Поле       | Тип      | Обязательно | Описание                     |
|-----------|----------|-------------|------------------------------|
| eventId   | string   | Да          | UUID события для дедупликации |
| eventType | string   | Да          | Тип: ORDER_CREATED, ORDER_PAID |
| orderId   | string   | Да          | UUID заказа                  |
| timestamp | string   | Да          | ISO 8601, UTC                |
| payload   | object   | Да          | Тело события (зависит от типа) |

### Гарантии
- Доставка: at-least-once.
- Консюмер обязан дедуплицировать по полю `eventId`.
```

## 7. Документация Helm-чарта

7.1. Каждый Helm-чарт содержит `README.md` с описанием:
- Назначение чарта.
- Параметры `values.yaml` с описанием каждого параметра, типом и значением по умолчанию.

7.2. Формат описания параметров:
```markdown
| Параметр                     | Тип    | По умолчанию | Описание                          |
|-----------------------------|--------|-------------|-----------------------------------|
| replicaCount                | int    | 2           | Количество реплик                 |
| image.repository            | string | —           | Docker-образ                      |
| image.tag                   | string | latest      | Тег образа                        |
| resources.requests.memory   | string | 256Mi       | Запрос памяти                     |
| resources.limits.memory     | string | 512Mi       | Лимит памяти                      |
| env.DB_URL                  | string | —           | JDBC URL PostgreSQL               |
```

## 8. Общие правила качества документации

8.1. Документация описывает «что» и «почему», а не «как». Код сам показывает «как». Если нужно пояснить «как» — это сигнал упростить код.

8.2. Не пиши документацию, которая устареет при следующем коммите. Пример плохой документации: «Сервис имеет 5 endpoint-ов» (станет неактуальным при добавлении шестого). Пример хорошей: «Полный список endpoint-ов — в OpenAPI-спецификации».

8.3. Каждое утверждение в документации должно быть верифицируемым. Не пиши «система высоконадёжна» — пиши «Circuit Breaker открывается после 5 ошибок подряд, retry выполняется 3 раза с интервалом 1 секунда (конфигурация в application.yml)».

8.4. Не дублируй информацию между видами документации. Если детали API описаны в OpenAPI — не повторяй список endpoint-ов в README. Ставь ссылку.

8.5. Используй единообразную терминологию. Если сущность называется `Order` в коде — не называй её «заявка» в одном месте документации и «заказ» в другом. Зафиксируй глоссарий терминов в README или отдельном файле.

8.6. Диаграммы описывай в текстовом формате (Mermaid, PlantUML), а не как растровые изображения. Текстовые диаграммы версионируются вместе с кодом и не требуют отдельного редактора для обновления.
